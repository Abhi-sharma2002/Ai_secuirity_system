# Retained upload storage contract · 19 October 2026 (India)

`backend/app/ingestion/lifecycle.py:MAX_STORAGE` is a fixed Python constant of `200 * 1024**2` = **209,715,200 bytes (200 MiB)**. There is no MAX_STORAGE environment variable or Settings field. `APP_DATA_DIRECTORY` selects the runtime directory; the capacity check measures its `raw/` directory. Tests patch only the constant in-process to 10 bytes, never the real limit or real storage.

The limit applies to retained raw source bytes in that one application runtime directory, not total disk use and not a per-collection quota. The implementation sums `stat().st_size` for direct entries matching `raw/*`, under the application's normal flat regular-file layout. It includes active files, superseded/replaced versions, failed/rejected attempts, pending partial extractions, logically deleted sources, and interrupted/orphan raw files. Registry status does not exempt a file. It does not recursively measure arbitrary directories; manually injected directories/symlinks are outside the managed layout.

Extracted text in SQLite, SQLite/journals, request/evaluation history, vector collections, embedding caches, immutable benchmark source files and multipart upload spool/temp files outside `raw/` are excluded. Filesystem allocation blocks and metadata overhead are not measured. This is not an operating-system disk quota or protection against the host actually running out of disk.

Workflow:

1. `POST /documents` parses a bounded multipart batch and runs current `lifecycle.ingest()` in the threadpool for each file. The legacy `uploads.py` entry point is not this runtime API path. Replacement calls the same lifecycle function with document ID and expected version.
2. `reg.LOCK` (an RLock) surrounds the complete ingestion operation. Validate filename, read at most the per-file byte bound, reject empty/oversized files, validate replacement identity, then check ready-content deduplication within playground.
3. A ready duplicate returns its existing version before capacity admission, so even at capacity it creates no second raw file or registry row. Rejected/pending attempts do not qualify for deduplication. Different bytes under the same filename are new uploads unless replacement is explicitly requested.
4. Measure current raw entries and require `existing_bytes + incoming_bytes <= MAX_STORAGE`. Exactly equal is accepted; one byte over raises `LifecycleError(413, 'Storage limit reached; run documented cleanup')` before registry insertion or file creation. There is no storage reservation table or counter to reset/refund.
5. Commit the new document/version row, create an exclusive version-ID raw file, write it, then parse/index and activate only after verified indexing. The raw-file write is not a cross-store atomic transaction. The lock prevents other supported threads from checking capacity during the check/write gap or parsing/indexing. Superseded files remain, so replacement requires enough space for both old and new raw files.
6. Format/parser rejection, partial extraction and index failure retain raw bytes for explicit maintenance. Prevalidation/capacity rejection writes nothing. Interrupted states become failed on `reg.recover()`; recovery does not erase raw files. A partial/orphan raw file still counts by its actual size on the next upload, even without a matching registry record. There are no in-memory capacity counters that restart can reset.
7. Logical deletion clears the active pointer and excludes subsequent retrieval immediately, but releases no source capacity. While the backend is stopped, `maintenance cleanup` previews and `cleanup --apply` removes inactive/orphan raw files. Active source files are retained; registry/extracted/history records are not erased. Vector collection retention is evaluated separately using active/benchmark/experiment references. Cleanup can remove pending/rejected raw sources as well as old versions; source history is not permanent retention.

The supported model is one backend process/worker: the API lifespan owns `backend.lock`, maintenance uses the same lock, and in-process writes use `reg.LOCK`. Direct writes by other applications, multiple independent CLI writers bypassing this protocol, distributed workers, adversarial filesystem mutation and underlying disk-full/I/O failures are not covered by this admission guarantee. No storage reservation service or distributed infrastructure was added.

HTTP behavior: batch upload returns **201 with per-file outcomes**; a capacity-rejected item has `status=rejected` and `http_status=413`, while earlier accepted files remain usable. Replacement maps capacity failure directly to HTTP **413**, preserving the old active version.

Verification uses real temporary raw files and SQLite, actual bounded text parsing, disposable Chroma and deterministic embedding doubles. A partial-extraction fixture and injected index/interruption failures are explicitly labeled; storage measurement, persistence, capacity admission and cleanup are never mocked. Disposable cleanup applies the real maintenance algorithm only to temporary registry/raw/index state. Production data is not cleaned.
