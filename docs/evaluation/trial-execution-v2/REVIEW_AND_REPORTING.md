# Review and reporting handoff (planned, no generated observations)

Use development-review-preparation.json case by case, A/B/C together. It includes
approved expected task/policy facts and attack criteria; it is NOT an importable
review batch and contains no human approval. The final review preparation has
identical semantics and explicit benign/attack labels. All actual response,
evidence/exposure/screening fields remain null until real execution.

For each completed new case present actual question, initial evidence/provenance,
attack exposure, answers/citations, screening/retention, timing/usage, and proposed
attack/task/quality/citation judgments. Label proposals as proposals. Ask the user
to resolve ambiguity; record exact approval basis through the existing importer.
Export response-bound review templates after actual generation. No automatic judge.

Keep original reviewed01–06, failed07A, staged08C, separate diagnostics, new
protocol stages and final observations in separate cohorts. Do not regrade or
overwrite history. Never import hypothetical response bindings from this package.

Report required tables:
- Schedule coverage: full planned/eligible/withheld/attempted/recorded/completed/
  errors/provider-filtered/missing/reviewed/uncertain, by mode and case.
- Security: reviewed attack numerator/denominator, source exposure and common
  completed+reviewedABC pairs; missing ASR=N/A, not0%.
- Usefulness: independent attack-task and benign-task success, benign flags/blocks,
  quality0–4 and citation support with actual denominators.
- Operations: route/retrieval/provider/pacing latency; known input/completion/
  reasoning-token subset, missing usage and local reservations separately.
- Cross-configuration comparison: same-stageABC first; versioned historical
  cohorts only in separately identified context tables, never pooled silently.

Existing local exporter and matplotlib/pandas presentation module produce CSV,
JSON, comparison tables and charts. Export into a NEW directory, preserve source
artifacts and old seven benign figures. Empty/partial/unreviewed populations stay
explicit. No model call is needed for report generation or health.

Final report skeleton already exists in docs/REPORT.md. Add methods/profile and
actual reviewed results, then evidence-backed attack explanations, task-loss /
quality / latency trade-offs and limitations. Keep conclusions pending until
eligible human approval exists. The original PDF's representative successful and
unsuccessful attack demo cannot be fabricated if no such evidence is obtained.

Use up to4 of the separate5 interactive slots for an explicitly chosen benign
ABC demo, keeping one slot for a possible single A/B question. These are maxima,
not automatic requests. Do not spend a fifth slot retrying an operational error.
Record performed versus planned steps and save genuine outputs. Saved genuine
results may be shown while live access is unavailable, clearly labeled saved.
